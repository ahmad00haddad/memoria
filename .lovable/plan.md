# خطة تطبيق توصيات التقرير التنفيذي

التقرير شامل (1328 سطر) ويقترح إعادة تأهيل المشروع من "نموذج أولي" إلى "منتج جاهز للإطلاق". أقترح التنفيذ على 7 مراحل متسلسلة، نوافق على كل مرحلة قبل بدئها.

> **ملاحظة مهمة:** التقرير يوصي بالانتقال إلى Next.js — لكن منصة Lovable مبنية على TanStack Start الذي يوفر نفس المزايا (SSR، SEO، Server Functions، Type Safety). سنحقق نفس الأهداف داخل البنية الحالية بدون هجرة مكلفة.

---

## المرحلة 0 — قرارات تأسيسية (قبل أي كود)
أحتاج إجاباتك على:
1. **الاسم النهائي:** Royal Lens Flow أم EliteCapture أم اسم ثالث؟ (سيُطبَّق في كل مكان: الهيدر، الفوتر، البريد، العقود، الـ metadata، الـ manifest، الـ favicon).
2. **نموذج العمل:** هل المنصة Marketplace (تتلقى العربون وتحوّله) أم SaaS + دليل (المصوّر يتلقى العربون مباشرة)؟
3. **سياسة قبول المصوّرات:** مفتوحة لأي شخص، أم مراجعة يدوية إلزامية قبل النشر؟

---

## المرحلة 1 — تنظيف الثقة وإزالة الادعاءات (3–5 أيام)
**الهدف:** إزالة كل ما هو وهمي أو مضلل قبل أي إطلاق.
- إزالة الأرقام والإحصائيات غير الموثقة من الصفحة الرئيسية و landing pages.
- إخفاء/تعليم التقييمات غير الموثقة بحجوزات مكتملة.
- استبدال صور stock العامة بـ placeholder محايد أو "أعمال قيد المراجعة".
- توحيد الاسم في: `__root.tsx` (title)، `manifest.webmanifest`، الفوتر، البريد، العقود، الـ OG tags.
- إضافة بادج "تم التحقق" فقط للمصوّرات اللواتي اجتزن مراجعة فعلية في DB.
- إعادة صياغة الـ Hero بحدّة: عنوان + وصف + CTA للعميل + CTA للمصوّرة + شارات ثقة قصيرة.

## المرحلة 2 — صفحات أساسية ناقصة (3–5 أيام)
- `/about` — من نحن، الكيان، العنوان، البريد، الفريق.
- `/contact` — نموذج تواصل + بريد الدعم + ساعات الرد.
- `/refund-policy` — سياسة الإلغاء والاسترداد (موجودة جزئياً في terms — تستحق صفحة مستقلة).
- `/faq` — أسئلة شائعة عملية مقسّمة عميل/مصوّرة.
- توحيد روابط الفوتر وإضافة عنوان الكيان وبريد الدعم.

## المرحلة 3 — تصلّب صفحة المصوّرة + البحث (5–7 أيام)
**صفحة المصوّرة** (لحظة الحسم):
- إضافة قسم شارات ثقة موحّد: تاريخ الانضمام، عدد الحجوزات المكتملة، نسبة الرد، زمن الرد، أول موعد متاح.
- شارة "التقييمات من حجوزات مكتملة فقط" (لأن المراجعة على التقييمات مفعّلة بالفعل).
- إبراز سياسة العربون/الاسترداد بوضوح فوق زر الحجز.
- CTA حجز ثابت (sticky) على الموبايل.

**صفحة البحث:**
- إضافة فلاتر ناقصة: نوع المناسبة، نسائي/مختلط، "متاحة في هذا التاريخ"، "سريعة الرد".
- إضافة خيارات ترتيب: الأنسب، الأعلى تقييماً، الأقرب للميزانية، الأسرع رداً.
- تحسين بطاقة النتيجة لإظهار "أول موعد متاح" و"زمن الرد".
- empty state أقوى مع اقتراحات.

## المرحلة 4 — تحسين رحلة الحجز (3 أيام)
الـ wizard من 3 خطوات موجود، لكن يحتاج:
- progress stepper أوضح + حفظ تلقائي في `localStorage` (لا تضيع البيانات عند الرجوع/التحديث).
- microcopy موحّدة بالعربية المباشرة من التقرير.
- شاشة نجاح بعد الإرسال: رقم الحجز، الحالة، الخطوة التالية، المسؤول الآن، متى تتوقعين الرد.
- تحسين validation messages بالعربية.

## المرحلة 5 — Onboarding المصوّرة (3–5 أيام)
الـ wizard الحالي 6 خطوات — توسعته لـ wizard كامل خارج الـ sheet:
- شاشة مستقلة `/onboarding` تظهر مرة واحدة بعد التسجيل.
- خطوات: حساب → تحقق → معلومات أساسية → مدن وخدمات → باقات → معرض → مراجعة وإرسال.
- مؤشر تقدّم محفوظ في DB (`profiles.onboarding_step`).
- لا يُنشر الملف حتى اكتمال الخطوات الإلزامية + قبول الأدمن (إن اخترت سياسة المراجعة).

## المرحلة 6 — تشديد البنية التقنية + الجودة (5–7 أيام)
- **Sentry** لتتبع الأخطاء (يحتاج DSN).
- **Analytics** عبر PostHog (events: search_started, photographer_viewed, booking_started/completed, payment_confirmed, onboarding_completed).
- **Smoke tests** عبر Playwright للمسارات الحرجة: تسجيل → onboarding → نشر، وبحث → عرض → حجز → دفع.
- **SEO:** التأكد من `head()` فريد لكل route، `sitemap.xml` يتضمن جميع المصوّرات المنشورة، JSON-LD `LocalBusiness` لصفحة كل مصوّرة.
- **Accessibility audit:** تباين الألوان، أحجام اللمس، RTL على كل مكوّن.
- **Performance:** lazy-load للصور، تحسين LCP على الموبايل.

## المرحلة 7 — هوية بصرية أصيلة (5–7 أيام — اختيارية، بعد ثبات المنطق)
- مراجعة Design tokens (الألوان، الخطوط، المسافات).
- اختيار خط عربي قوي (Tajawal/IBM Plex Sans Arabic/Rubik) بدلاً من الافتراضي.
- تقليل التدرجات/اللمعان الذي يوحي بالقالب.
- توحيد أسلوب الصور والأيقونات (Lucide وحدها).
- بناء صفحة مرجعية للمكوّنات (`/design-system` داخلية).

---

## ما لن نفعله (حسب توصية التقرير)
- لا هجرة إلى Next.js — TanStack Start يغطي نفس الحاجات.
- لا تطبيق Native قبل ثبات الويب.
- لا حملات تسويق قبل اكتمال المراحل 1–4.

## القرار المطلوب منك الآن
1. **أجب عن أسئلة المرحلة 0** (الاسم + نموذج العمل + سياسة القبول).
2. **حدد من أين نبدأ:** هل ننفّذ المراحل بالتسلسل (1 → 7)، أم تريد البدء بمرحلة معيّنة؟
3. **هل توافق على تخطّي المرحلة 7 مؤقتاً** والتركيز على المنطق والثقة أولاً؟

بمجرد ردّك، أبدأ بالمرحلة المطلوبة فوراً.
